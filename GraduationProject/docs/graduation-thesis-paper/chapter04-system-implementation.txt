第4章  系统实现

4.1  引言

本章围绕第3章设计，对系统实现情况进行说明。实现采用 npm 工作区划分服务端与前端两个子工程：服务端基于 Node.js 与 Express 提供 HTTP 接口与业务编排；前端基于 React 与 Vite 构建单页应用，根目录一条命令可同时启动两端，便于本地联调与答辩演示。持久化方面，聊天会话与消息、知识库及研究任务等写入本地 SQLite 数据库，库表在首次启动时由初始化脚本创建并建立索引；用户注册信息等以 JSON 文件形式落盘，由用户仓储层读写。外部依赖（大模型、嵌入、联网检索、SMTP）均通过环境变量注入，未配置时相关接口返回明确错误而非崩溃。以下按模块介绍关键实现点，并在相应位置给出截图占位与必要的 PlantUML 出图源码（渲染后插入排版稿；分隔线及说明勿粘入 Word 正文）。

4.2  认证与用户模块

4.2.1  注册、登录与鉴权

认证相关 HTTP 路由集中在 server/src/index.js；用户数据的增删改查由 server/src/auth/userStore.js 读写 data/users.json；令牌在 server/src/auth/jwt.js 中签发与校验，载荷中仅保存用户名等必要字段，过期时间由配置决定。需要登录的接口统一挂载 server/src/auth/middleware.js 中的 requireLogin：从请求头 Authorization 读取 Bearer 令牌，解析出用户名后再进入业务处理；解析失败直接 401，不进入业务逻辑，避免半鉴权状态。

注册走 POST /api/auth/register，落库用户名、密码、邮箱，并生成 6 位注册验证码及有效期；邮件发送成功后，用户在页面提交 POST /api/auth/verify-email-code 完成邮箱验证（emailVerified 置为真）。注册与发码前均检查 SMTP 是否已配置，未配置则返回 503，提示部署时需补全邮件环境。验证码过期可调用 POST /api/auth/resend-verification 重发（带冷却限制）。登录提供两条路径：POST /api/auth/login 使用用户名与密码，密码登录前校验邮箱已验证；或先 POST /api/auth/send-login-code 向邮箱发登录验证码，再 POST /api/auth/login-with-code 换取令牌。忘记密码时 POST /api/auth/forgot-password 向邮箱发送重置令牌，对未注册邮箱仍返回统一成功响应，降低邮箱枚举风险；用户在重置页提交新密码，对应 POST /api/auth/reset-password。POST /api/auth/logout 服务端仅返回成功，实际登出由前端删除本地令牌完成。页面刷新后用 GET /api/auth/me 携带令牌恢复当前用户，无效时返回 user: null，前端据此跳转登录页。

4.2.2  个人会话与消息持久化

会话与消息由服务端仓储层封装，对应数据库中的会话表与消息表。接口层提供会话列表、新建会话、按会话拉取消息、删除会话以及更新会话标题或「绑定知识库」等能力。追加消息时同步维护会话的最近更新时间；在用户发出首条用户消息时可自动生成会话标题摘要，并对单会话消息总量做上限控制，仅保留最近若干条以保证性能。

4.3  智能对话模块

4.3.1  对话接口与上下文组装

核心入口为已登录用户调用的「发送消息」接口（POST /api/chat）。请求体以当前会话编号与用户问题为主，并可附带对话风格、是否强制走深度研究、知识库检索偏好及简单问答时的生成长度等可选参数；查询参数 sync=1 可要求同步等待研究结束，debug=1 可返回额外诊断字段，便于开发调试。服务端先确认会话归属并读取近期对话作为上下文，再综合用户选择与规则判断本次是否需要「深度研究」：chatRouteMode 为 simple/deep 时强制走对应分支；环境变量可全局强制；否则对寒暄类问题用启发式规则直接走简单问答，其余可调用轻量 LLM 路由 JSON 判断 needsResearch。

未走深度研究时，若该会话绑定了知识库，则先做向量检索并按阈值筛选命中片段，将检索结果以附录形式并入本轮提示；检索异常时记录日志但不中断主流程，附录为空继续生成。随后将系统说明、历史轮次与当前问题经上下文预算裁剪后送入大模型生成回复，写入会话消息表并向前端返回本轮结果及 ragHitCount、ragSuppressedByMinScore 等统计信息，便于界面展示是否命中知识库等。生成失败时将错误信息写入助手消息正文，避免前端长时间无响应。

走深度研究时，将上文与当前问题整理为研究主题（可同样附带知识库检索摘要），在数据库中登记研究任务并记录协调过程；同会话若已有研究在进行则返回 409。研究管线在后台默认异步执行，完成后把生成的报告或错误说明作为一条助手消息写入当前会话，助手消息 meta 可关联 taskId；前端通过任务编号轮询进度直至结束，并可打开管线弹窗查看 trace 映射的阶段节点。

4.3.2  ReAct 编排与内置工具注册实现

工程在服务端单独实现了一套与主对话接口解耦的 ReAct 编排子系统：由编排器按迭代上限循环调用大模型，解析其返回的工具调用与终稿字段，再交由工具执行层完成计算器、时间、回显等内置能力的调用，并通过注册表管理可扩展工具；新增工具只需实现统一接口并在启动时 register，无需修改编排器核心循环。该子系统体现第3章中的 ReAct 范式，可作为「工具增强对话」的可复用组件；当前主会话仍以直连大模型与深度研究管线为主，二者在架构上预留了后续对接或合并的余地。论文与答辩中若以聊天+RAG+研究为主演示，ReAct 可作为扩展能力说明，避免与主路径混淆。

（若论文答辩需演示工具循环，可在此补充截图占位：图4-8 调用该子系统的调试脚本或未来接入后的对话效果截图。）

4.4  知识库与 RAG 模块

4.4.1  文档分块与入库

知识库能力通过服务端一组 REST 接口对外提供：支持创建集合、按条或批量写入文本分块等。上传或录入的正文先按固定策略切分为片段，再调用嵌入接口生成向量，与原文一并写入知识库分块表，供后续检索使用。

（截图占位：图4-9 知识库「新建集合」或集合详情页截图。）

（截图占位：图4-10 分块列表或上传/ingest 操作成功后的界面截图。）

4.4.2  向量检索与多库合并、阈值过滤

单库可按向量相似度查询；对话侧若绑定了多个知识库，则分别检索后在服务端合并结果，按相似度排序并截断为前若干条，再按用户或默认设定的最低分门槛整体过滤：若最高分仍低于门槛，则本轮不向模型注入知识库片段，避免噪声干扰。

4.4.3  对话中 RAG 片段注入与引用策略

命中片段在服务端格式化为带编号与相似度说明的附录文本，拼入系统侧提示，引导模型在确有依据处使用统一形式的引用标记。简单问答与深度研究共用相近的提示拼装与语气约束思路；在深度研究中，上述附录还可并入研究主题描述，并转换为研究管线内部使用的「文档列表」供证据提炼阶段消费。

（截图占位：图4-11 同一会话绑定知识库后，助手回复中出现引用标记或命中统计展示的截图（若前端展示 ragHitCount）。）

4.5  深度研究模块

4.5.1  Planner 子问题规划实现

规划阶段由规划智能体独立调用大模型完成。实现上先构造规划角色提示词，将用户给出的研究主题（可含会话上文与知识库检索摘要）要求模型输出严格 JSON 格式的研究计划，内容包括计划标题、子问题列表及每条子问题对应的检索关键词、来源提示与优先级，并附带少量验收要点，用于约束后续写作是否覆盖关键方面。提示词中限定子问题数量为 1～5 个，要求角度互不重复、紧扣主题，避免机械套用固定申论式拆题；模型返回后，编排流程还会对子问题做语义去重并截断上限，进一步降低检索噪声。

规划调用支持配置生成长度与温度，并配合统一的模型重试与 JSON 解析容错：若输出不完整或解析失败则按策略重试，避免规划环节阻塞整条流水线。规划开始时将任务状态置为「规划中」，协调节点向过程轨迹写入阶段说明；规划成功后把结构化计划写入任务产物存储，并记录子问题数量等决策信息，供后续检索、阅读与写作各阶段按子问题逐条推进，同时支持前端轮询进度与事后回放。

4.5.2  联网检索与网页抓取/降级实现

资料搜集由检索与抓取分工完成，任务状态置为「收集中」，主要动作写入过程轨迹。检索智能体按各子问题关键词调用联网检索服务，获取标题、链接与摘要；若会话已绑定知识库，则先对子问题做向量检索，将命中分块与网页条目合并。抓取智能体对候选链接拉取正文并清洗，设超时与长度上限；遇反爬或抓取失败时降级为检索摘要，保证子问题仍可继续。知识库命中条数与相关度较高时可跳过外网检索以省时，否则在知识库结果外再补充少量网页来源；编排器按并发上限并行处理子问题，去重后形成统一文档列表写入搜集产物，作为后续证据提炼与报告写作的输入。

4.5.3  Reader、Writer、Critic 阶段实现

证据提炼、章节写作、质量检查与可选全文润色分别由阅读、写作、审查三类智能体对应的服务端逻辑实现，在研究编排流程中按子问题依次衔接：阅读阶段将上游文档列表抽取为论点、依据与链接等证据单元；写作阶段据证据生成分节标题、摘要、正文段落及引用来源；多个子问题可并行处理，并发数可配置以兼顾速度与外部接口压力。

各阶段调用大模型时采用统一的重试与 JSON 解析容错策略，限定最大重试次数，避免模型输出格式不稳导致整条流水线失败。阅读或写作单次解析失败时不终止整项任务，分别退化为基于原文档的要点摘要，或基于已有证据片段的节级草稿，并在过程轨迹中标注降级情况。全部小节完成后，审查阶段逐节检查来源是否充分、引用是否多样，以及是否存在缺乏证据支撑的数值或年份表述；来源不足时触发补充检索并重新阅读、写作该节，断言风险过高时重写该节以弱化具体数字。协调节点另行为全文生成概述与结论，失败则跳过；审查通过后还可选做全文润色，最终结果写入结构化产物库与 Markdown 研究报告，供前端展示。

4.5.4  Trace 记录与产物组织

4.7  本章小结

本章依据第3章设计方案完成系统实现。工程上采用前后端分离：服务端承担用户认证、多会话持久化、发送消息路由、知识库检索增强及深度研究多阶段编排；前端提供登录注册、聊天主界面、知识库管理与研究进度展示。认证模块实现注册验证码、双通道登录与令牌鉴权；对话模块在同一入口区分简单问答与深度研究，并支持会话级知识库绑定；知识库模块完成分块入库与多库检索合并；深度研究模块落地规划、资料搜集、阅读写作与质量审查各阶段，并具备抓取与解析失败时的降级策略及过程轨迹记录。工具增强编排作为可扩展能力单独实现，与主路径解耦。实现与第3章架构、模块及数据设计总体一致，下一章将开展功能与场景测试说明。
